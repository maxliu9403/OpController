# OpController UI 设计审查与优化方案

## Skill 来源

本次审查使用 `canvas-design` skill 的方法：先建立视觉哲学，再把页面问题映射为空间、节奏、层级、色彩和工艺问题。该 skill 已安装到 `/Users/max/.codex/skills/canvas-design`，重启 Codex 后会作为正式 skill 加载。

## 视觉哲学：秩序控制台

`秩序控制台` 的核心不是装饰，而是把复杂运营动作压缩成清晰、可被信任的空间秩序。界面应该像一张精密的调度图，所有信息都有明确坐标：Provider 是环境，流程是路线，Profile 是载体，批次是执行，结果是回声。页面不靠大段解释建立信任，而靠稳定的间距、可预测的区域、明确的状态和经过反复打磨的动作路径建立信任。

空间必须服务于“先看哪里、再做什么”。高频操作应靠近当前上下文，危险操作应远离主路径并带确认。复杂信息不应被平均摊开，而应被分层折叠：概览只展示决策所需，详情只在用户进入编辑、排查或复盘时展开。最终界面应像经过长时间校准的仪表盘，每个模块都显得是被反复推敲后留下来的，而不是功能自然堆积后的结果。

色彩应成为状态语言，而不是装饰语言。蓝色只表达主动作和当前焦点，绿色只表达可运行或成功，橙色表达等待、风险或未完成，红色只表达失败和危险。节点小图标和微色彩可以保留，但必须克制，像工程图中的标记，而不是营销页面的彩带。每一次强调都要付出理由，没有理由的颜色就是噪音。

视觉节奏应偏“苹果式内部工具”：轻、薄、准确，留白不奢侈但足够呼吸。卡片边框、表格线、阴影和毛玻璃效果要统一减噪，避免同一屏出现太多材质。字体层级要更坚定：页面标题、区域标题、字段标签、状态标签、说明文字各司其职，不互相抢戏。最终效果应体现顶级工匠式的克制：看起来简单，但每个像素都像被调整过。

交互工艺必须优先保护运营同事。凡是会改变流程结构、Provider、Profile 组、批次执行数据的动作，都必须有明确进入态、退出态和确认态。用户不能“无意中编辑”，也不能“不知道自己在编辑”。锁定态、编排态、试运行态、执行态、复盘态要有一致的视觉符号和一致的行为规则。

## 总体判断

当前 UI 已经从早期“说明型长页面”进化到“工作台”，但仍有三个结构性问题：

- 页面正在变成“功能充分但决策路径偏散”的工具，尤其流程编排页同时承担流程库、编辑器、测试会话和 YAML，认知负担偏高。
- 状态语言还不够系统化，同样是“可操作、锁定、未配置、运行中、失败”，不同页面的表现方式不完全一致。
- 空间节奏还不够统一，有些页面已是固定画布，有些页面仍像表单堆叠；窗口放大后的动态利用率还可以继续优化。

## P0：必须优先优化

### 1. 建立全局状态语言

目标：所有页面都使用同一套状态枚举、颜色、图标和交互规则。

建议定义统一的 `StatusBadge` / `StatePill` 组件，覆盖：

- 流程：只读查看、编排中、未关联 Profile 组、可运行、不可启动。
- Provider：未配置、未连接、已连接、同步中、同步失败。
- 批次：草稿、待运行、运行中、已暂停、取消中、已取消、成功、部分成功、失败。
- 定时：启用、停用、冲突跳过、等待下次运行。
- 任务行：等待、执行中、成功、失败、跳过、取消。

落地要求：

- 不再直接散落使用 AntD `Tag color`。
- 状态组件内部完成中文翻译、颜色、图标、tooltip。
- 红色只用于失败和危险动作，避免日常提醒滥用红色。

### 2. 流程编排页拆成“三态工作台”

当前流程页已经有锁定/编排保护，但视觉结构还可以更科学。

建议三态：

- `浏览态`：上方流程库为主，下方画布只读，动作库折叠或弱化。
- `编排态`：流程库压缩成一行上下文条，画布成为主舞台，测试会话保留。
- `调试态`：右侧测试会话升级为调试面板，展示当前步骤、截图、失败原因、重试入口。

关键调整：

- 编排态下，流程列表区域可压缩为“当前流程上下文条”：流程名、Provider、Profile 组、保存、锁定。
- 动作库不要和测试会话同权重，动作库是输入，画布是主体，测试会话是辅助。
- 全流程测试按钮应在画布顶部主动作区，单步测试在节点编辑抽屉中。

### 3. 所有破坏性或上下文切换动作进入统一 Guard

目标：任何会丢失上下文的操作都必须经过同一套 `EditorGuard`。

覆盖动作：

- 新建流程。
- 切换流程。
- 删除正在查看或正在编辑的流程。
- 切换 Provider。
- 修改流程分组。
- 导入流程覆盖当前上下文。
- 离开页面或切换侧边栏菜单。

交互标准：

- 无修改：提示确认切换即可。
- 有修改：保存并继续、放弃修改、取消。
- 未保存草稿：保存为新流程、放弃草稿、取消。

### 4. Provider 管理页从配置页变成“连接中心”

当前 Provider 页功能齐全，但配置、范围、Profile 清单还是偏表单化。

建议结构：

- 顶部：Provider 切换 + 连接状态 + 测试连通性 + 同步按钮。
- 中部左：管理范围分组选择。
- 中部右：配置项，只有当前 Provider 需要的字段。
- 下部：Profile 清单，只展示已管理范围内 Profile。

BitBrowser、NSTBrowser、ixBrowser 应保持同一 UI 模式，但配置项不同：

- ixBrowser：本地 API 地址/端口。
- NSTBrowser：本地 API 地址 + API Key。
- BitBrowser：Local Server 地址。

## P1：高收益优化

### 5. 批次页改成“导入 -> 校验 -> 启动”的单向流程

当前批次页已支持 Excel/profile_id 映射，但视觉上仍像普通表单。

建议改成三段式：

- 选择流程：显示绑定 Provider、Profile 组、可运行 Profile 数。
- 导入表格：显示校验结果、前 5 行预览、profile_id 匹配统计。
- 启动确认：槽位、Provider 健康检查、预计任务数、风险提示。

启动按钮只在校验通过后高亮。导入后无需再出现“草稿批次”概念，避免重复语义。

### 6. 定时页改成“计划卡片 + 表格副本”

定时任务不是批次列表的复制，它更像自动化计划。

建议：

- 创建区用向导：流程 -> Excel -> 执行频率 -> 确认。
- 计划列表用卡片或紧凑表格，突出“下次执行时间”和“Excel 副本状态”。
- 每个计划支持查看/替换表格/编辑频率/启停/删除。
- 不展示时区字段，固定北京时间，只在 tooltip 说明。

### 7. 结果页改成“复盘仪表盘”

结果页要帮助运营 1 分钟内定位失败原因。

建议布局：

- 左侧：批次列表，支持流程名搜索和结果状态过滤。
- 右上：批次摘要，成功率、耗时、Provider、Profile 范围。
- 右中：失败原因分类和错误码排行榜。
- 右下：任务行列表，内部滚动，支持导出当前过滤结果。

任务详情建议采用 Drawer，而不是在主表格塞太多列。

### 8. 监控页保留但降噪

监控页首版不用复杂，但要更像“事件流”。

建议：

- 按类型过滤：Provider、Batch、Task、Schedule、Runtime。
- 事件分级：信息、警告、错误。
- 错误事件可一键跳转到对应批次或任务。

## P2：视觉系统优化

### 9. 统一空间栅格

建议建立固定 spacing token：

- 页面边距：16 / 20 / 24。
- 卡片内边距：12 / 16。
- 面板间距：12。
- 表格行高：紧凑 44，普通 52。
- 工具栏高度：40。

目前页面内存在 12、14、16、18、24 混用，短期可用 CSS 变量统一。

### 10. 收敛材质和阴影

当前毛玻璃、阴影、边框、半透明背景较多。建议：

- 主背景保持 `#f5f5f7` / `#1c1c1e`。
- 卡片只保留极轻阴影。
- 内部面板优先用边框和浅背景，不重复叠加大阴影。
- 表格容器不再使用强阴影，减少视觉噪声。

### 11. 重构按钮优先级

建议按钮语义：

- Primary：当前页面唯一主动作，如“开始编排”“启动批次”“保存计划”。
- Default：次动作，如“导入”“导出”“刷新”。
- Text/Icon：局部行操作，如复制、编辑。
- Danger：删除、取消运行、放弃修改。

同一区域不要出现多个 Primary。

### 12. 表格动作列标准化

所有表格动作列建议统一：

- 行主动作最多 1 个。
- 次动作进入 `更多` 菜单。
- 终态记录不展示无意义动作。
- 运行态展示“取消/暂停/恢复”，失败态展示“重试”，成功态不展示动作。

## 页面级建议

### Dashboard

当前可作为运营入口，但建议增加“今日待处理”而不是只展示统计。

建议卡片：

- Provider 连接异常。
- 今日计划。
- 最近失败批次。
- 可继续编排的草稿流程。

### Provider

核心目标是降低接入成本。

建议新增：

- “连接检查步骤”引导：启动浏览器客户端 -> 确认 Local API 地址 -> 测试连通性 -> 同步 Profile。
- Provider 卡片显示 ixBrowser / NSTBrowser / BitBrowser 的差异配置。
- Profile 清单增加“复制 profile_id”。

### Workflows

核心目标是“运营能放心编排”。

建议：

- 浏览态默认只看流程库。
- 编排态最大化画布。
- 节点编辑抽屉中展示定位细节，不在节点卡片中展示。
- 节点卡片只展示业务语言：打开页面、等待、点击、输入、滚动。
- 节点异常修复入口统一放在试运行结果里。

### Batches

核心目标是“避免错跑”。

建议：

- 启动前确认弹窗必须展示：Provider、流程、Profile 组、Excel 行数、槽位数。
- 表格校验失败时，错误要按类型分组。
- 已导入 Excel 可替换、删除、重新校验。

### Schedules

核心目标是“自动化计划可理解”。

建议：

- 创建计划不允许手填数据，只能导入 Excel。
- 每个计划显示当前 Excel 文件名、导入时间、有效行数。
- 编辑计划时必须保留或替换 Excel 副本，不能隐式丢失。

### Results

核心目标是“失败复盘”。

建议：

- 默认按最近失败/部分成功排序。
- 失败原因卡片可点击过滤任务行。
- 任务详情 Drawer 包含截图、步骤时间线、错误原因、重跑建议。

## 建议实施顺序

1. 抽象 `StatusBadge`、`ConfirmGuard`、`PageToolbar`、`TableActionMenu` 四个基础组件。
2. 先改流程页，因为它是最复杂、最高频、最影响运营上手的页面。
3. 再改 Provider 页，让三家 Provider 接入体验统一。
4. 再改批次和定时页，统一 Excel/profile_id 校验与启动确认。
5. 最后改结果页和监控页，完善复盘体验。

## 验收标准

- 非技术运营同事能在不解释按钮含义的情况下判断当前是否可编辑、是否可启动、是否有风险。
- 同一状态在所有页面表现一致，不再出现英文状态或颜色含义不一致。
- 一个页面同一时刻只有一个主动作。
- 切换流程、新建流程、切换 Provider、启动批次等高风险动作都有一致确认路径。
- App 窗口放大后，核心内容区域能自然扩展，而不是固定高度留空。
